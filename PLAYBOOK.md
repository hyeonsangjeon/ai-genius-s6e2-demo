## Deferred setup reference

Do not execute setup during repository cleanup or presentation preparation. The commands
below are retained for a later, explicitly authorised setup. Use this independent repository,
not the upstream author's repository, and the `hyeonsangjeon` account for GitHub writes.

Requirements: Python 3.13, `uv`, Azure CLI, azd 1.35+ and GitHub CLI. Confirm the selected
subscription, region, model availability, quota and authentication before provisioning.
The imported model capacities are GPT-5.4-mini 400, GPT-5.5 300 and text-embedding-3-small 50;
these are configuration requests, not verified availability or a cost estimate. The deployment
region remains undecided. Install the locked dependencies as CI does.

From `sample/`, only after setup resumes:

```bash
azd extension install azure.ai.agents --version 1.0.0-beta.13
azd extension install azure.ai.projects --version 1.0.0-beta.8
azd extension install azure.ai.connections --version 1.0.0-beta.9
uv venv --python 3.13 && source .venv/bin/activate
uv pip install --require-hashes -r agent/requirements.txt -r requirements-dev.txt

# Replace both placeholders with the selected target before running.
azd env new ai-genius-s6e2-demo --subscription <SELECTED_SUBSCRIPTION_ID> --location <SELECTED_REGION>
azd env set GITHUB_REPOSITORY hyeonsangjeon/ai-genius-s6e2-demo
azd up
export FOUNDRY_PROJECT_ENDPOINT="$(azd env get-value FOUNDRY_PROJECT_ENDPOINT)"
python evaluation/evaluate.py --register-only
```

`azd up` provisions the project, models, monitoring, agent and GitHub identity. Its hooks also
write GitHub `demo`/`production` environments and variables, and grant the deployed agent
embedding access. Preprovision reuses a saved `GITHUB_REPOSITORY` before considering origin:
verify that value rather than assuming a remote change updates it. These hooks are not part
of repository creation or push. After an authorised deployment, inspect the actual Demo 2
trace before claiming hybrid search or successful tool calls.

## Baselines after execution resumes

Each gate compares a dataset with a committed baseline. A person reviews and replaces that
baseline; the pipeline never moves its own bar. The imported scores are upstream references.
Preserve their `source` metadata, and establish a measured baseline for the selected environment
before using the gates for release. Changed questions, references or judges require fresh
measurements; never attach new fingerprints to old scores.

Once cloud execution is separately authorised, configured and explicitly enabled, these
billable manual workflows generate replacement baseline artifacts:

```bash
gh workflow run agent-pr.yml --repo hyeonsangjeon/ai-genius-s6e2-demo --ref main -f write_baseline=true
gh workflow run agent-main.yml --repo hyeonsangjeon/ai-genius-s6e2-demo --ref main -f mode=baseline-holdout
gh workflow run agent-main.yml --repo hyeonsangjeon/ai-genius-s6e2-demo --ref main -f mode=baseline-drift
```

Inspect specific run IDs with `gh run list --repo hyeonsangjeon/ai-genius-s6e2-demo`.
Use `gh run download <RUN_ID> --repo hyeonsangjeon/ai-genius-s6e2-demo --name <ARTIFACT_NAME>
--dir <REVIEW_DIRECTORY>` to download into separate local review directories. Review completed
results and provenance before replacing tracked baselines. A main push starts cloud promotion
only when Actions and the repository opt-in are both enabled.

**Demo 1 — model comparison.** Show a prepared Foundry comparison with the same task and
conditions. Model Router is a topic to explain or verify separately, not a capability established
by the sample's fixed GPT-5.4-mini configuration.

**Demo 2 — starting agent.** Use the dated dinner question, then “Yes, there will be wine.”
The source scenario expects a Hospitality Lead requirement and a recorded delegate while Tim
is away. The Marcus scenario distinguishes Category Manager approval from a line-manager
delegation. Check dates and current fictional documents before stating the expected answer.
Right or wrong, one answer is not evidence of overall quality.

**Demo 3 — trace.** Inspect that same run's model/tool calls, inputs, results, timings and errors.
The trace shows what happened; it does not establish that the answer was correct. State whether
policy retrieval used hybrid search or keyword fallback.

**Demo 4 — evaluation.** Open a completed holdout run, inspect a failing question and its judge
reason, then compare development and holdout. Show actual variation and failures, not only
averages. Imported reference scores must not be labelled as a run in this environment.

**Demo 5 — Agent Optimizer.** Compare candidate scores with variation, then inspect changes to
instructions and tool/parameter descriptions. Distinguish useful rules from copied policy facts.
If no useful optimiser result is available, show a manually reviewed configuration and say how
it was produced. The current reviewed configuration equals the baseline, so it is not evidence
of improvement. Describe a score gain only when the selected run supports it.

**Demo 6 — CI/CD.** Planned path: development gate, holdout on `-dev`, review, drift, release
approval and `-release` deployment. Show each outcome only after an actual run. For a deliberately
bad candidate, identify the failing check and whether configured branch rules prevent merging;
keep that PR unmerged. The plain-script fact check flags new amounts, dates, IDs and names, but
can miss facts. A person still reviews the change.

**Continuous evaluation.** A settings walkthrough can explain how a rubric applies to live
traffic without reference answers. Do not enable it during routine presentation preparation.

## CI/CD

When enabled, the PR and promotion workflows share `_agent-eval.yml`: deploy an isolated agent,
evaluate a dataset and compare with a baseline. These are configured roles, not existing deployments.

| Agent | Intended purpose |
| --- | --- |
| `purchasing-advice-demo` | Live questions and optimisation; CI does not deploy here |
| `purchasing-advice-demo-pr-<number>` | PR development-set evaluation after offline checks |
| `purchasing-advice-demo-dev` | With cloud opt-in: main holdout, review and drift |
| `purchasing-advice-demo-release` | Release after holdout, review, drift and release approval |

The repository-level `ENABLE_CLOUD_DEMOS == 'true'` condition protects promotion `target` and
`release`, PR `development`, and reusable `evaluate`. Keep it unset or false while paused.
Actions are also disabled for now. Re-enabling Actions alone does not opt in to cloud jobs.
With Actions enabled, offline PR lint, formatting, request and prompt-fact checks can run
without Azure. Do not enable the flag or dispatch a workflow as a side effect of a source push.

Gates compare score drops with configured tolerances. The PR tolerance 0.07 is imported from
upstream; it is not a noise estimate measured here. Release requires no failed or unscored drift
cases. A red check blocks merging only when branch rules require the relevant checks, including
“1. Offline checks” and “2. Development set vs baseline”. PR agents are not deleted automatically;
plan their cleanup separately after authorised execution.

## Troubleshooting after execution resumes

These are diagnostic pointers, not permission to change deployment, quota or roles now.

| Symptom | What to inspect |
| --- | --- |
| Policy search reports `keyword` | `fallback_reason`, embedding freshness, identity access and role propagation; do not claim hybrid search |
| OIDC federation mismatch | Compare the subject and saved repository binding with `hyeonsangjeon/ai-genius-s6e2-demo` |
| Missing repository parameter or GitHub variables | Selected azd environment and pre/postprovision results; verify the target before rerunning a hook |
| Cloud jobs skipped | Actions disabled or `ENABLE_CLOUD_DEMOS` unset/false; intentional while paused |
| Workflow waits | Agent concurrency lock or production review |
| Missing/mismatched baseline provenance | Fresh measurements from a known configuration, followed by review |
| Registered judge differs from local JSON | Review the definition change, then explicitly register and refresh affected baselines |
| Unscored questions | Actual error: rate limit, authentication or evaluator failure; missing scores are not successes |
| Model quota failure | Requested capacity, remaining quota and model/SKU availability; do not change existing allocations automatically |
